# app-ios

The iOS app (`nl.appeal.fava`) and its AutoFill extension
(`nl.appeal.fava.autofill`), both SwiftUI over the `FavaEngine` package in
`../engine-jsc/swift`. Read `../engine-jsc/AGENTS.md` first: the engine, its
threading and the unlocked-session contract are explained there.

## The project is generated

`project.yml` is the source of truth; `Fava.xcodeproj` and the two Info.plists
are generated by XcodeGen and gitignored. Change targets, settings, Info.plist
keys or capabilities in `project.yml`, never in Xcode's UI (it would be
overwritten). XcodeGen comes from the root flake's dev shell on macOS.

- `make project`: regenerate (also done by `build`/`test` when the spec or the
  file list changed). Then open `Fava.xcodeproj`.
- `make build`, `make test`: on the first available iPhone simulator, or the
  one `SIMULATOR=<udid>` names. Both run `make -C ../engine-jsc build` first,
  because the JS bundle is a generated resource of the engine package.
- Off macOS every target is a no-op, so the root `make` still works in the
  container.

## Layout

| Path        | What                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| `Shared/`   | Compiled into both targets: the app group, the Keychain access group, the vault file and the session store |
| `App/`      | The app. `VaultModel` owns the one engine and its lifecycle                                                |
| `AutoFill/` | The credential provider extension, one-time codes only                                                     |
| `Tests/`    | Unit tests hosted by the app, so they run with its entitlements                                            |

## Identifiers

Team `HW2XFJ2L7B`. Both targets share the app group `group.nl.appeal.fava`
(the vault file) and the Keychain access group
`HW2XFJ2L7B.nl.appeal.fava.shared` (the unlocked session). The group names
reach the code through the `FavaAppGroup`/`FavaKeychainGroup` Info.plist keys,
which the build fills in, so they are written down only in `project.yml` and the
entitlements. A device build needs these App IDs and the app group registered
with the team; Xcode does that with automatic signing. Simulator builds do not.

## Lock versus close

`VaultModel.lock()` is the user locking the vault: favalib's contract deletes
the unlocked session with it, so the next unlock takes the password. Going to
the background calls `close()` instead: the engine shuts down and the vault
leaves memory, but the session stays, so coming back takes only Face ID, the
same as a relaunch. Keeping the session at all is opt-in ("Unlock with Face
ID" in settings).

## AutoFill

The extension only unlocks from the saved session, and only after Face ID.
Without one, or if unlocking with it fails (which deletes it), it shows "Open
Fava to unlock" and never asks for the password: a password unlock runs argon2
at 64 MiB, too much to risk under the extension's memory limit. It does not
connect to the sync server. Enable it on the device under Settings > General >
AutoFill & Passwords.

## Not there yet

import/export. The engine supports all of them.
