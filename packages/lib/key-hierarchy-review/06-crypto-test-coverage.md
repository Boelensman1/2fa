# 06 — Nothing pins the KDF parameters or the stored format

**Verdict:** weak — this is what makes every other change dangerous
**Status:** done
**Priority:** P1, but **do it before [01](01-kdf-parameters.md)** — done, so
that prerequisite is satisfied
**Touches:** `tests/CryptoProviders/kdf-vectors.test.ts`,
`tests/subclasses/PersistentStorageManager.test.mts`, `tests/fixtures/`

## Finding

**The argon2 parameters are pinned by nothing.** `grep -rn
"argon2\|iterations\|memorySize" packages/lib/tests/` returns zero hits. The
closest thing is `tests/CryptoProviders/compare-node-browser.test.ts:231`,
`'Node and Browser createSyncKey produce the same result'`, which asserts only
that the two providers agree with _each other_ — change `iterations: 256` to `1`
in both files and that test still passes.

There is **no KDF test vector anywhere**, so a parameter change is silently
vault-breaking for every existing user with a fully green suite. This is the
most dangerous single fact in the review.

**The stored format is pinned shallowly.**
`tests/subclasses/PersistentStorageManager.test.mts:96-105` asserts the key set
of the JSON envelope — but `encryptSymmetric` is mocked to the identity function
for that test (lines 74-79), so the actual ciphertext encoding (the
`base64(iv) + ":" + base64(ct)` concatenation) is never asserted.

**There is no checked-in fixture of a real encrypted vault.** Every test builds
its vault fresh in `beforeAll` via `createFavaLibForTests`, so nothing would
catch a format regression against previously-stored data.

## What to do

1. **A KDF test vector**: fixed password + fixed salt + explicit parameters →
   expected hash, asserted against a hardcoded constant. Both providers.
2. **A checked-in v1 fixture vault** (`LockedRepresentation` JSON + its
   password) that must still open. This is the regression gate for
   [01](01-kdf-parameters.md), [02](02-ciphertext-authenticity.md) and
   [03](03-storage-versioning.md) — all three change the stored format.
3. Unmock `encryptSymmetric` in at least one `PersistentStorageManager` test so
   the real ciphertext encoding is asserted.

Two small test files. Cheap, and it converts the format work from "hope" to
"checked".

## How to verify

Deliberately change `iterations` in both providers and confirm the suite now
goes red — first on the test vector, then on the fixture vault.

## Resolution

Done 2026-09-16, in three parts. [01](01-kdf-parameters.md) is unblocked: the
KDF parameters and the stored encoding are now pinned by absolute values, so a
change to either fails the suite instead of failing a user.

**Item 2 — the frozen v1 fixture vault** landed first, with
[03](03-storage-versioning.md): `packages/lib/tests/fixtures/vault-v1.json` is a
real v1 vault plus its password, opened by `tests/fixtures.test.mts` on both the
node and browser providers. Its expected OTPs were cross-checked against an
independent RFC 6238 implementation, so it pins argon2id → RSA-OAEP → AES-CBC →
TOTP as genuinely correct, not merely self-consistent.

`tests/fixtures/README.md` records the standing convention — one frozen fixture
per storage version, generated by the code at the commit that shipped it, never
regenerated, and no generator script checked in (it would silently start writing
the _new_ format the moment [01](01-kdf-parameters.md)/[02](02-ciphertext-authenticity.md)
land, and invites someone to destroy the gate by "refreshing" it).

**Item 1 — the KDF test vectors** are `tests/CryptoProviders/kdf-vectors.test.ts`.
Two vectors, each asserted in two deliberately separate layers:

- The **algorithm anchor** calls `argon2id` with the v1 parameters written out
  as literals. It is permanent: after [01](01-kdf-parameters.md) moves new
  vaults to stronger parameters, _these_ parameters must still produce _this_
  hash or no vault written before the change can be opened again. It also
  catches a `hash-wasm` upgrade that changes behaviour under fixed inputs.
- The **policy assertion** calls the shipped code —
  `generatePasswordHash(salt, password)` — and requires it to equal the anchor,
  i.e. the defaults are still the v1 parameters. This is the one that reddens
  the moment someone edits `iterations`, `memorySize` or `parallelism`. Whoever
  lands [01](01-kdf-parameters.md) must move it consciously to a v2 vector and
  leave the v1 anchor in place; the file says so at the assertion.

The password-hash vector deliberately uses **the password and salt of
`vault-v1.json` itself**, so it isolates the argon2 step of the fixture the
suite already opens: when both go red, the vector says which layer moved. The
sync-key vector uses a 32-byte shared secret and a device-id salt, the shape
`createSyncKey` is really called with (`SyncManager.mts:664,696`), and is run
through **both** provider classes — unlike `generatePasswordHash`, which node
imports from the browser file (`node/cryptoLib.mts:31`) and so exists once,
`createSyncKey` is implemented twice.

Both expected values were computed with `hash-wasm` **and** independently
reproduced with the reference P-H-C implementation (`nixpkgs#libargon2`), which
agreed byte for byte. That is what makes them vectors rather than a recording of
our own output, and the test file quotes both `argon2` command lines so a reader
can re-verify without trusting this repo.

**Item 3 — the identity mock is gone.** `'should return a locked
representation'` in `tests/subclasses/PersistentStorageManager.test.mts` now
uses `vi.spyOn`, which calls through, instead of replacing `encryptSymmetric`
with the identity function. It keeps the call-count assertion, and adds what the
mock made impossible: the envelope really is `base64(iv) + ":" + base64(ct)`
with exactly one separator, a 16-byte IV and a non-zero whole number of
AES-256-CBC blocks, and it decrypts with the vault's own symmetric key back to
the expected `VaultState` — which is the same assertion block as before, now
applied to real plaintext rather than to a string that was never encrypted.

**Verified by mutation**, each change reverted afterwards:

| Mutation                                               | Result                                                                                                                                               |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iterations: 256` → `255` in `generatePasswordHash`    | policy assertion red, anchor green, `fixtures.test.mts` red                                                                                          |
| `iterations: 256` → `255` in **both** `createSyncKey`s | both provider vectors red — while `compare-node-browser.test.ts`'s "produce the same result" test stays green, which is exactly the hole this closes |
| `':'` → `'\|'` in node's `encryptSymmetric`            | envelope assertion red, first and by name (`expected length 2, got 1`)                                                                               |
