# app-ios

The iOS app (`nl.appeal.fava`) and its AutoFill extension
(`nl.appeal.fava.autofill`), both SwiftUI over the `FavaEngine` package in
`../engine-jsc/swift`. Read `../engine-jsc/AGENTS.md` first: the engine, its
threading and the unlocked-session contract are explained there.

## The project is generated

`project.yml` is the source of truth; `Fava.xcodeproj` and the two Info.plists
are generated by XcodeGen and gitignored. Change targets, settings, Info.plist
keys or capabilities in `project.yml`, never in Xcode's UI (it would be
overwritten). XcodeGen comes from the root flake's dev shell on macOS.

- `make project`: regenerate (also done by `build`/`test` when the spec or the
  file list changed). Then open `Fava.xcodeproj`.
- `make build`, `make test`: on the first available iPhone simulator, or the
  one `SIMULATOR=<udid>` names. Both run `make -C ../engine-jsc build` first,
  because the JS bundle is a generated resource of the engine package.
- Off macOS every target is a no-op, so the root `make` still works in the
  container.

## Layout

| Path        | What                                                                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Shared/`   | Compiled into both targets: the app group, the Keychain access group, the vault file, the session store, entry search and the domains an entry claims (`SiteDomains`) |
| `App/`      | The app. `VaultModel` owns the one engine and its lifecycle                                                                                                           |
| `AutoFill/` | The credential provider extension, one-time codes only                                                                                                                |
| `Tests/`    | Unit tests hosted by the app, so they run with its entitlements                                                                                                       |

## Identifiers

Team `HW2XFJ2L7B`. Both targets share the app group `group.nl.appeal.fava`
(the vault file) and the Keychain access group
`HW2XFJ2L7B.nl.appeal.fava.shared` (the unlocked session). The group names
reach the code through the `FavaAppGroup`/`FavaKeychainGroup` Info.plist keys,
which the build fills in, so they are written down only in `project.yml` and the
entitlements. A device build needs these App IDs and the app group registered
with the team; Xcode does that with automatic signing. Simulator builds do not.

## Lock versus close

`VaultModel.lock()` is the user locking the vault: favalib's contract deletes
the unlocked session with it, so the next unlock takes the password. Going to
the background calls `close()` instead: the engine shuts down and the vault
leaves memory, but the session stays, so coming back takes only Face ID, the
same as a relaunch. Keeping the session at all is opt-in ("Unlock with Face
ID" in settings).

## AutoFill

The extension only unlocks from the saved session, and only after Face ID.
Without one, or if unlocking with it fails (which deletes it), it shows "Open
Fava to unlock" and never asks for the password: a password unlock runs argon2
at 64 MiB, too much to risk under the extension's memory limit. It does not
connect to the sync server. Enable it on the device under Settings > General >
AutoFill & Passwords.

iOS suggests a provider on a one-time code field only for identities the
provider registered, so the app registers one per entry and domain
(`CredentialIdentities`, with the domains from `SiteDomains`: the entry's
matchers, where Regex matchers and entries without matchers give none, and the
codes list marks those entries) whenever it refreshes the entries, and removes
them all on reset. Locking leaves them: picking one still takes Face ID. A
picked suggestion carries the entry id, and the extension fills that code
without showing its list. iOS keeps the domains and labels outside the vault's
encryption.

iOS empties a provider's store behind its back (switching the provider off and
on, some OS updates), so the app forgets what it registered every time it comes
to the foreground and writes the store again on the next refresh. Settings >
AutoFill shows whether Fava is on as a provider, how many codes have a
website, and what the app last registered, with "Register again". It cannot
show what iOS holds: `ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)`
returns nothing in the app, for every type and for each registered domain by
name, while the suggestions do show up in Safari.

The extension serves three kinds of request, and finishes each its own way
(`CredentialProviderViewController.Mode`):

- One-time code: the bar's suggestion, or its list of codes.
- Text to insert (`ProvidesTextToInsert`): long-press any field > AutoFill >
  Fava. This works where Safari did not recognise a code field (and so offers
  no suggestion), or the site is not registered.
- Password: iOS lists Fava in its password sheet on login forms although it
  declares `ProvidesPasswords: false`. A password request cannot carry a code,
  so picking one copies it (local to the device, expiring with the code) and
  cancels the request.

On a one-time code field, the list matches the entries against the site iOS
names (shown small at the top of the list). One match is filled straight away,
without the list.

When the request names a site and the user picks a code from "Other codes", the
extension offers to remember the site: it adds a `Host` matcher to the entry,
for exactly the host iOS named, and registers the identity with iOS directly.
It uses `Host` rather than `BaseDomain` because iOS may have named only the
registrable domain, and a `BaseDomain` for that would claim every site under
it. The edit is saved to the vault file; favalib keeps it queued and sends it
to the sync server the next time the app connects.

## Sync

Settings > Sync takes the server address and its shared secret (one setting,
stored in the vault), lists the paired devices, and "Add a device" starts
pairing as the device that has the vault, showing the code as text and as a QR
code.

Joining another device's vault starts on the first-run screen ("Join a vault
from another device"): it creates a placeholder vault under a password for this
device, then asks for the server and the pairing code. Pairing replaces the
vault's contents but not this device's keys, so the password stays per device
and a saved session keeps working. `isJoining` is persisted, so a relaunch
mid-join comes back to the join screen. favalib fires
`connectToExistingVaultFinished` on success and on a cancel alike; the model
tells them apart by whether the vault now lists another device. "Start over"
deletes the placeholder vault. Joining is offered only on first run, so it
never replaces a vault with codes in it: to join with a vault already there,
Settings > "Reset Fava" deletes it first (`VaultModel.reset()`, behind a
confirmation that says how many codes go and whether other devices have them).

`ws://` works only to servers on the local network (`NSAllowsLocalNetworking`);
anything else needs `wss://`. Going to the background shuts the engine down,
which also drops a pairing in progress.
